# Askovo: implementation status

## Agent Native service frame (2026-11-26)

- **Opportunity Research**: turn an industry, technology or product idea into real user problems, substitutes, counterevidence and an evidence-backed opportunity.
- **Demand Validation**: turn a demand assumption or product concept into participant screening, local experiment records and an explicit validation result; public recruitment and deployment require separately authorized services.
- **Product Intelligence**: turn a live product into durable research watches, incremental evidence and a changing view of users, competitors and demand.
- The host agent chooses the research path. Askovo supplies collection, analysis, experiments and evidence constraints. Local experiments and structural checks are not recruitment, demand proof or product acceptance.

## Watch scheduling, notification delivery and model cost (working tree, 2026-11-26)

- `watch serve` runs recurring reviews without a host agent. When a separately authorized research-run plan exists, it executes that bounded plan before review and reports only newly collected source records; without a plan it keeps local review only. Notification events commit with watch history and source fingerprints exclude only runtime files. `watch notifications` lists undelivered events, while injected adapters require receipts and failed delivery stays pending.
- Semantic reports separate deterministic zero-token work from OpenAI-compatible `usage` totals and unmeasured responses. Candidate and critic calls accumulate prompt, completion and total tokens without implying a dollar cost.
- Existing eligibility, deployment, `watch execute` and task-result projections remain in force. The optional serve path installs no daemon, external notification channel or second real review by itself.
- **Verification:** 1125 tests and the packaged demo pass. An isolated wheel also passes `watch create → serve → notifications → injected delivery`; empty receipts stay failed and pending. No external research collection, public recruitment or second real review is claimed.

## Research execution hardening (working tree, 2026-11-26)

- `decide status` adds a read-only `ovo.task-result/1` business projection alongside the existing C-01 fields. It separates running, waiting for external input, user decisions, partial results, delivery and inability to complete; blocked scopes and resume references stay explicit. CLI and MCP share the same status function, and delivery still does not mean decision approval.
- Landing enrollment and outcome windows are enforced at HTTP execution time. Late new assignments and out-of-window conversions do not enter the registered metrics; existing participants can convert during a separately registered outcome window.
- `capture plan invitations` creates private bearer-token invitations only for research-ready participants. Landing eligibility registries and assignments store token hashes, so clearing a cookie does not duplicate a participant and aggregate exports contain neither raw tokens nor participant refs.
- `experiment landing deploy` runs a separately authorized deployment adapter bound to the experiment source hash. A matching deployment id, HTTPS URL and observation time produce `DEPLOYMENT_REPORTED`; with `verify_url: true`, an independent HTTPS read must expose the same `askovo-source-sha256` before `DEPLOYMENT_VERIFIED`. Neither state proves traffic or participation.
- `watch execute` composes an already prepared and named-authorized research-run action list with the existing local due review. It never creates/authorizes a plan or promotes evidence. CLI, Skill and MCP expose the new actions; real recruitment, hosting and scheduling still need external service acceptance.

## Longitudinal diary studies (working tree, 2026-11-25)

- `experiment diary create/import/status/export` freezes the objective, prompt, consent, window, ascending schedule and screened participant pseudonyms before local entry import. Accepted entries need source/consent and timezone-aware submission; withdrawal stores no response and blocks later entries. SQLite enforces the registration fingerprint, participant/date uniqueness and conflict-safe deduplication.
- Status reports late and missing scheduled cells without sending reminders. Aggregate export excludes participant references and response text. Counts remain descriptive and do not prove participation, representativeness, demand or product acceptance. CLI, Skill and MCP share the implementation; public recruitment and external notifications remain outside this runtime.
- Verification: 1107 full-suite tests pass. The rebuilt wheel passes create/import/duplicate-import/status/export in an isolated environment, with source-spec hash unchanged and no participant ref or response text in the aggregate. `A3-DIARY-STUDY-01` is synthetic, not real participation.

## Participant screening (working tree, 2026-11-25)

- `capture plan screen` produces a named, source-bound roster with separate eligibility, consent and research readiness. Eligible participants need evidence refs; only accepted consent becomes research-ready, while pending/declined/withdrawn stay excluded. Stable participant refs deduplicate and conflicts fail. CLI, Skill and MCP `screening_export` share the implementation; source plans and contacts are not mutated and no recruitment occurs.

## Prototype task observation (working tree, 2026-11-25)

- `experiment prototype create/import/status/export` registers task instructions and success criteria before local observation. Named, consent-bound observations carry participant pseudonym, attempt, time, success, duration, assistance and errors; SQLite enforces registration fingerprint, participant limits and idempotent conflict-safe imports. Aggregate task rates, median duration and shared experiment export stay descriptive and exclude participant IDs. - Optional `validation_mode=mvp_behavior` adds pre-registered `repeat_window_hours` and aggregate activation/retention projections over the same task observations. Activation is a first successful registered task; retention requires another success after the registered interval. Rates use participant and activated-participant denominators respectively, empty denominators stay null and exports use aggregate observations without participant IDs.

## R0 experiment and pagination corrections (working tree, 2026-11-25)

- Optional `validation_mode=price_sensitivity` freezes currency, price definition and distinct non-negative price points per arm. Status, aggregate source hashes and shared design retain price metadata; observed registration intent remains non-payment evidence.
- Landing experiments now freeze population, window, per-arm sample target and comparability at creation. A persistent registration fingerprint rejects source-file drift and post-hoc export substitutions. New design revisions use a separate experiment version with `revision_of`, previous design hash, reason and registration time; old observations stay with their original design.
- Arctic pagination processes each response inside the loop, advances `before`, exits on short/empty pages and refuses a non-decreasing repeated cursor. Offline tests cover short, full→empty and duplicate-page sequences without live collection.

## Local recurring research watches (working tree, 2026-11-25)

- `watch resolution` projects missing/failed/gapped reviews and paused watches into `ovo.problem-resolution/1`. It never auto-retries or mutates evidence/decisions; the shared `ovo_acceptance resolution` CLI independently evaluates the next action. CLI, Skill and MCP action `resolution` share the projection.
- `askovo watch create|status|run|execute|pause|resume` persists named review watches, cadence, due state and append-only run history. `run` is an explicit local review tick; optional authorized local issue exports use the existing delta engine. `execute` first runs a separately prepared and named-authorized bounded research-run plan, then performs the same review. Neither path promotes canonical evidence or mutates decisions; `execute` never creates or authorizes a collection plan.
- State and history writes use the study transaction lock and strict reads. Paused watches do not run; resume makes the watch due. A failed review is recorded as failed and scheduled later, never rewritten as a successful observation.
- CLI, Skill and MCP (`askovo_research_watch`) expose the same actions. Neither command is a daemon or autonomous semantic judge; real host scheduling and external collection services remain separate acceptance work.

## Needs-first delivery and account policy (v2.24.0, 2026-11-25)

- `askovo deliver STUDY --kind needs` projects the canonical chain into a business-first needs report: conclusion, requirement changes, product/business impact and next actions; evidence IDs, audit states and quotes stay in the appendix. `--baseline` compares a previous study and separates added/removed chains from evidence and status changes.
- Semantic candidates bind to a full-corpus snapshot covering text plus source, evidence level, method, participant and eligibility metadata. New counter-evidence or changed research qualification returns `STALE_CORPUS`; `--against-snapshot` is required for a clearly labelled historical export. `askovo semantic support` adds a candidate+critic-bound support sidecar; `not_assessed` and contradicted support block export, unsupported needs a named override, partial exports with a warning.
- Host Agent mode writes a request for the host to answer, then validates nonce, exact quotes, record ids and forbidden conclusion fields on import. Candidate ids and hashes stay local; named review is still required.
- `account_policy.py` persists platform account id/handle, account tier and `collect` daily caps in `.askovo/account-quotas.json`; rotation resolves profile by platform plus account. Publishing quotas are never reused as collection quotas; unknown tiers/caps stay unknown.

## Constrained semantic candidates (v2.23.0, 2026-11-24)

- `askovo analyze <study> --semantic` adds an optional, off-by-default candidate layer on top of the deterministic analysis. An OpenAI-compatible model may propose themes, mechanisms and counterexamples, but every candidate must cite an existing `record_id` plus an exact quote substring, `unknowns` is mandatory, and `status` stays `unverified`. Model-declared `evidence_level`, demand claims and `validated` status are rejected before storage.
- A critic pass (deterministic scan plus optional model critic) records counterexamples, coverage gaps, alternative explanations and missing evidence before any candidate can be reviewed. Named CLI `askovo semantic review` then gates export; the review binds both candidate and critic hashes, and either changing requires a fresh review. MCP cannot accept/reject on a human's behalf. Accepted candidates become `collected_corpus_statement` E2 observations whose quote provenance is preserved and whose inferred theme stays unverified. Nothing enters `evidence.jsonl` automatically.
- Without `ASKOVO_LLM_BASE` / `ASKOVO_LLM_MODEL` the command falls back to deterministic analysis. Non-loopback endpoints require explicit `--allow-external`; remote endpoints must use HTTPS, and all model/embedding redirects are refused. Ambiguous cross-platform record ids are rejected before citation. Optional embedding retrieval caches only text hashes and vectors, and falls back to keyword matching. The offline stub validates the contract, not real model recall quality.
- **Verification:** 43 dedicated tests plus the full 1002-test CLI/MCP/observation suite pass; see `docs/semantic-candidates.md`.

## Opportunity map and external research

`askovo do` scaffolds the five-layer opportunity map automatically when the routed mode is Discover; `askovo explore <study>` remains available to rebuild it; the layers are empty structures with questions and an item schema, not findings. `askovo external-research <study> --command <id> --authorize` runs a host-supplied research adapter and stores its JSON output as candidate sources (`evidence_level: null`, `review_required: true`); authorization is mandatory because the command runs with the operator's privileges. A-06 tightened that boundary: the child environment is built from an allowlist (never inherited), only a signed registry entry with a matching adapter SHA-256 may run, stdout/stderr have hard caps that fail instead of truncating, every run gets its own `ext-<utc>-<random>` id, the output path cannot escape the study, and a URL is never fetched or verified (A29-A33). `--trusted-local` is the explicit, audited escape hatch for a one-off local command. Neither feature promotes anything into evidence.

## Research modes

`askovo mode` and the `research_mode` field in `askovo route --json` return a deterministic Discover/Validate/Optimize entry contract: mode, mode source, entry node, rotated seven-node order, upstream hypotheses, questions, first actions, stop conditions and boundary. The entry changes what to answer first; it never waives the evidence requirement for any node.

- Recommendation is task-sized: it infers decide/discover/define/design/validate/launch/operate/review, selects a minimum sufficient team, lists deferred roles with reasons, and produces an output contract for primary/supporting deliverables, format, length, audience, structure, evidence display, visuals and industry expression. `--task`/`--scale` override; default scaffolding generates only the task's output templates, with `--all-templates` as an explicit expansion.
- Workplans contain task/scope/output contracts plus catalog/industry hashes, role/SOP/KPI/template references, bound `PRxx.node/edge` targets, owners and work states. Empty chains are rejected, multi-chain studies require `--chain`, stateful workplans cannot be force-overwritten, and atomic generation leaves no partial workbench.
- `deliver --kind role` and `--kind lifecycle` are canonical projections, not template-authored findings. Workplan/catalog/industry freshness and reference validity join full audit and decision review; legacy studies without a workplan remain compatible.
- KPI targets start null. Commercial KPI targets require canonical `business.success_metrics` references. SOP `done` never upgrades evidence, demand, decision, release, clinical, safety, compliance, production or causal states.

## v2.10.0 depth: A1–A3

- **A1 — independent StopDecision:** `stop` no longer receives the same positive utility score as research actions. Its `askovo.stop-decision` gate can rank first only when three explicit declarations all hold: evidence is sufficient for the decision, remaining unknowns cannot change it, and continued research value is below its cost/risk. Missing or contrary declarations make stop ineligible; the criteria, basis references and restart condition stay visible. These are declared decision inputs, not fabricated measurements.
- **A2 — executable offline analysis:** for `unwritten_node` and `claim_needs_decision` gaps with existing `02-data/normalized.jsonl` or `evidence.jsonl`, the analyze candidate is preferred and executable through the same CLI/MCP loop. It reuses `analyze_study`, performs no network access, writes an input-fingerprinted gap result plus `04-findings/loop-executions.json`, and records `open → analyzed` with human semantic revision/assessment still required. It does not rewrite the canonical chain or demand judgments. Collection keeps its envelope authorization and Design gate; experiment and external-evidence actions remain candidates only.
- **A3 — adversarial DecisionRecord revision:** after an initial supporting record, registered same-context evidence with provenance and a pre-recorded `contradicts`/counter-evidence relation can trigger a new version. The deterministic default is `hold` plus `needs-validation` and a one-step confidence downgrade (`high → medium → low → very-low`), with a substantive safe replacement of the current product/business recommendation; `--recommendation` is only an optional human override. An evidence ID without a contradiction mapping is rejected. Replay retains before/after recommendations, confidence, evidence relations, snapshots and change-log references. Newly mapped evidence is not promoted into a demand judgment, supporting causal state or validated node, and the revision does not prove causality.

Build: SURE reasoning, evidence contracts, authorization, acceptance and delivery. Reuse: existing source connectors; evaluate Crawl4AI/Scrapy for collection and Docling for documents only as optional adapters. Core remains standard-library-only. The optional `askovo_document` MCP tool shares the same local extraction adapter as `askovo document`, and writes only to explicit local paths. New document ingestion uses an optional Docling installation; no vendored fork or mandatory core dependency.

Research loop: `askovo loop plan/authorize/run/status/report/assess` detects gaps from the same audit verdicts, generates deterministic queries per gap and eligible source, executes them inside an authorized envelope (allowed platforms, per-action cap, round and record budgets), re-audits after each round and writes `04-findings/loop-candidates.json`, `04-findings/loop-analysis/<gap>.json`, `04-findings/loop-executions.json` for executable offline analysis, `04-findings/loop-evaluations.json` and `05-audit/research-loop-summary.md`. Candidates carry `proposed_evidence_level: null`: only human review assigns E0–E5 and links records to a demand judgment. A candidate advances its gap to `collected`; the analysis action advances it to `analyzed` and never closes it; `loop assess` is the only path to `resolved`/`unresolvable` and requires a named operator plus evidence (`resolved`) or a reason (`unresolvable`). The envelope is an operational bound, not tamper protection; platform policy, `allowed_sources`, adapter switches and the Design gate remain the enforcing controls. MCP can plan/status/report/run but cannot authorize or assess.

Recovery: completed actions are checkpointed before analysis; an interrupted `running` action blocks replay. The loop records `interrupted_run` and requires inspection before replanning. Inspect collected files and provenance before preparing a replacement plan. Never reset blindly. Execution is serialized using an OS file lock on macOS/Linux. `research` authorization binds the actual action fields; `loop` authorization binds the envelope hash.

## Test integrity and cross-ticket integration

Two guard suites sit beside the feature tests. `tests/test_suite_integrity.py`
turns "silently skipped test" into an immediate red: every `tests/test_*.py` must
collect exactly as many cases as it defines `def test_`, a class with `test_*`
methods that does not inherit `unittest.TestCase` is named, `@unittest.skip*`
decorators must be whitelisted with an optional-dependency reason, and module-level
`load_tests` / `setUpModule` / `tearDownModule` hooks are flagged. This exists
because the A lane twice shipped a green suite whose tests were never collected.

`tests/test_askovo_decision_service_integration.py` covers the A-lane seams: one
lifecycle from dry start through the human authorization gate, run, brief, delta
sync and approval (monotonic product state, `partial` brief with gaps, one
`needs_re_review` verdict shared by the brief and the delta, byte-identical
approved DecisionSnapshot); MCP `askovo_decide_start` / `_status` / `_result` and
the `decide` CLI reporting the same task, state, reason code and next action; A-06
external candidates staying out of the brief's evidence with no level promotion;
and a deleted cited evidence record marking both the brief (delivery blocked) and
the delta (exit 1) stale.
