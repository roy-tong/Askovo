# Askovo: implementation status

Reviewed 2026-11-04 against the **v2.13.0 release**. Available means local implementation, not production validation on every platform.

| A03–A05 | Source routing, authorization and bounded collection | Available for supported connectors and offline exports; the loop may only use `scope.allowed_sources` with an enabled adapter or a declared fixture; interrupted actions require review |

## Research modes

`askovo mode` and the `research_mode` field in `askovo route --json` return a deterministic Discover/Validate/Optimize entry contract: mode, mode source, entry node, rotated seven-node order, upstream hypotheses, questions, first actions, stop conditions and boundary. The entry changes what to answer first; it never waives the evidence requirement for any node.

## Role operating system depth

- `skills/askovo/assets/role-catalog.json` is the single role-definition source: 80 exact role families, 340 KPI definitions, 517 SOP steps, 257 deliverables and 1,859 template sections. `industry-contexts.json` adds ten overlays without forking the five SURE base-domain packs.
- `askovo roles list/show/recommend/scaffold/template` and `askovo_roles` share one CLI implementation. AI can be a capability overlay on a hardware primary industry; base-domain conflicts and ambiguous candidates stay visible.
- Recommendation is task-sized: it infers decide/discover/define/design/validate/launch/operate/review, selects a minimum sufficient team, lists deferred roles with reasons, and produces an output contract for primary/supporting deliverables, format, length, audience, structure, evidence display, visuals and industry expression. `--task`/`--scale` override; default scaffolding generates only the task's output templates, with `--all-templates` as an explicit expansion.
- Workplans contain task/scope/output contracts plus catalog/industry hashes, role/SOP/KPI/template references, bound `PRxx.node/edge` targets, owners and work states. Empty chains are rejected, multi-chain studies require `--chain`, stateful workplans cannot be force-overwritten, and atomic generation leaves no partial workbench.
- `deliver --kind role` and `--kind lifecycle` are canonical projections, not template-authored findings. Workplan/catalog/industry freshness and reference validity join full audit and decision review; legacy studies without a workplan remain compatible.
- KPI targets start null. Commercial KPI targets require canonical `business.success_metrics` references. SOP `done` never upgrades evidence, demand, decision, release, clinical, safety, compliance, production or causal states.

## v2.10.0 depth: A1–A3

- **A1 — independent StopDecision:** `stop` no longer receives the same positive utility score as research actions. Its `askovo.stop-decision` gate can rank first only when three explicit declarations all hold: evidence is sufficient for the decision, remaining unknowns cannot change it, and continued research value is below its cost/risk. Missing or contrary declarations make stop ineligible; the criteria, basis references and restart condition stay visible. These are declared decision inputs, not fabricated measurements.
- **A2 — executable offline analysis:** for `unwritten_node` and `claim_needs_decision` gaps with existing `02-data/normalized.jsonl` or `evidence.jsonl`, the analyze candidate is preferred and executable through the same CLI/MCP loop. It reuses `analyze_study`, performs no network access, writes an input-fingerprinted gap result plus `04-findings/loop-executions.json`, and records `open → analyzed` with human semantic revision/assessment still required. It does not rewrite the canonical chain or demand judgments. Collection keeps its envelope authorization and Design gate; experiment and external-evidence actions remain candidates only.
- **A3 — adversarial DecisionRecord revision:** after an initial supporting record, registered same-context evidence with provenance and a pre-recorded `contradicts`/counter-evidence relation can trigger a new version. The deterministic default is `hold` plus `needs-validation` and a one-step confidence downgrade (`high → medium → low → very-low`), with a substantive safe replacement of the current product/business recommendation; `--recommendation` is only an optional human override. An evidence ID without a contradiction mapping is rejected. Replay retains before/after recommendations, confidence, evidence relations, snapshots and change-log references. Newly mapped evidence is not promoted into a demand judgment, supporting causal state or validated node, and the revision does not prove causality.

Build: SURE reasoning, evidence contracts, authorization, acceptance and delivery. Reuse: existing source connectors; evaluate Crawl4AI/Scrapy for collection and Docling for documents only as optional adapters. Core remains standard-library-only. The optional `askovo_document` MCP tool shares the same local extraction adapter as `askovo document`, and writes only to explicit local paths. New document ingestion uses an optional Docling installation; no vendored fork or mandatory core dependency.

Research loop: `askovo loop plan/authorize/run/status/report/assess` detects gaps from the same audit verdicts, generates deterministic queries per gap and eligible source, executes them inside an authorized envelope (allowed platforms, per-action cap, round and record budgets), re-audits after each round and writes `04-findings/loop-candidates.json`, `04-findings/loop-analysis/<gap>.json`, `04-findings/loop-executions.json` for executable offline analysis, `04-findings/loop-evaluations.json` and `05-audit/research-loop-summary.md`. Candidates carry `proposed_evidence_level: null`: only human review assigns E0–E5 and links records to a demand judgment. A candidate advances its gap to `collected`; the analysis action advances it to `analyzed` and never closes it; `loop assess` is the only path to `resolved`/`unresolvable` and requires a named operator plus evidence (`resolved`) or a reason (`unresolvable`). The envelope is an operational bound, not tamper protection; platform policy, `allowed_sources`, adapter switches and the Design gate remain the enforcing controls. MCP can plan/status/report/run but cannot authorize or assess.

Recovery: completed actions are checkpointed before analysis; an interrupted `running` action blocks replay. The loop records `interrupted_run` and requires inspection before replanning. Inspect collected files and provenance before preparing a replacement plan. Never reset blindly. Execution is serialized using an OS file lock on macOS/Linux. `research` authorization binds the actual action fields; `loop` authorization binds the envelope hash.
