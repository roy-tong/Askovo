# 核心概念

SURE 不生产“洞察”，它管理**判断与证据之间的距离**。

## 1. 证据等级 E0–E5

| 等级 | 材料中直接出现 | 允许的判断 | 不能用来支持 |
| --- | --- | --- | --- |
| E0 | 活动、角色或场景背景 | 这个场景出现在材料中 | 问题存在、方案被接受 |
| E1 | 未满足任务、目标或困难 | 问题被明确表达 | 替代方案、付费意愿 |
| E2 | 当前做法、绕行、失败或切换成本 | 已观察到替代方案及摩擦 | 方案接受、市场规模 |
| E3 | 对研究方案的明确接受或偏好 | 方案在给定条件下被接受 | 付费、持续使用 |
| E4+ | 价格锚点、购买意愿或付费表达 | 出现直接商业意图 | 已发生的付费行为 |
| E4− | 拒绝、取消、退货或放弃 | 出现直接负面商业行为 | 正面的商业结论 |
| E5 | 付费持有、部署、持续使用、复购、扩张 | 出现已实现的行为证据 | 总体比例、因果 |

**关键约束**：证据等级是“材料里直接出现了什么”，不是“我们推断出了什么”。一条评论说“如果便宜我会买”是 E4+ 的意图，不是 E5 的行为。

## 2. 五类证据角色

| 角色 | 作用 | 缺失的后果 |
| --- | --- | --- |
| `direct_solution` | 直接使用/接受目标方案的人 | 不知道方案是否被需要 |
| `open_scene` | 在开放场景描述问题的人 | 只看到被方案筛选过的人 |
| `substitute_rejector` | 用过替代方案后拒绝/放弃的人 | 看不到反证与失败模式 |
| `post_purchase_support` | 购买后遇到问题的人 | 看不到留存与真实成本 |
| `control` | 背景对照（不相关场景/人群） | 无法判断信号是否只是普遍现象 |

`plan` 会把样本配额分配到这些角色；`check` 会检查是否覆盖。缺角色时，报告只能输出“研究状态”，不能输出需求结论。

## 3. 一条证据记录

```json
{
  "record_id": "support-0042",
  "user_role": "现场维修工程师",
  "scene_trigger": "双手正在拆装设备，需要确认下一步操作",
  "task_outcome": "在不中断操作的情况下取得准确指导",
  "current_substitute": "放下工具后查看手机或呼叫远程专家",
  "friction_cost": "中断操作，并增加沟通往返",
  "consequence": "维修时间延长，复杂步骤可能返工",
  "evidence_level": "E2",
  "evidence_basis": "材料同时描述了当前做法和造成的中断",
  "corpus_role": "open_scene",
  "source_family": "professional_forum",
  "source_ref": "source-record-0042",
  "normalized_text_hash": "sha256:..."
}
```

这条材料能支持“当前做法存在摩擦”，不能单独支持“工程师接受 AI 眼镜”“愿意付费”或“市场占比 30%”。

完整字段见 [数据契约](data-contract.md)。

## 4. 需求判断与 `validated`

一条判断不是一句结论，而是一组可追溯的引用：

```json
{
  "id": "D01",
  "title": "受监督的移动巡检补足固定摄像头盲区",
  "user_role": "远程宠物主人",
  "scene": "收到告警或长时间外出时，需要检查另一个房间",
  "task": "在决定是否干预前确认现场",
  "current_substitute": "固定摄像头或请邻居帮忙",
  "friction": "盲区、额外安装、邻里沟通成本",
  "consequence": "延迟回家或不必要的往返",
  "solution": "会话式的移动家庭巡检",
  "acceptance_conditions": "物理遮挡、房间边界、明确的会话开始、可见的录制状态",
  "problem_evidence_ids": ["R01", "R02"],
  "solution_evidence_ids": ["R03"],
  "commercial_evidence_ids": ["R04", "R06"],
  "counter_evidence_ids": ["R05", "R07"],
  "status": "validated",
  "confidence": "low",
  "gaps": ["仅合成样例"],
  "next_test": "真实两周试点，预注册隐私拒绝与留存门槛"
}
```

要标为 `validated`，必须同时满足：

1. 同一角色、场景、任务贯穿；
2. 问题链有 `E1` 或 `E2`；
3. 方案链有 `E3`；
4. 商业/行为链有 `E4+` 或 `E5`；
5. 有反证记录（默认强制）；
6. 所有引用 id 都存在于 `evidence.jsonl`。

`sure audit` 会逐条检查这些条件。声称 `validated` 但缺链的判断会被标为 **`exceeds_evidence`**，退出码为 1。

## 5. “通过”意味着什么

`check` 和 `audit` 的 `pass` 只说明：

- 结构和配置的门槛过了；
- 证据链在该门槛下自洽；
- 引用可追溯。

它不证明：

- 需求真实存在；
- 样本代表总体；
- 市场规模或份额；
- 因果关系。

这句话会固定出现在 `audit.md` 与 `report.md` 的边界段。

## 6. 禁止推断

默认写进 `study.json`：

- 不从便利样本推断总体流行度；
- 不把记录当独立用户（除非有合法的身份解析）；
- 不把检索地区当用户常住地；
- 不把功能提及频率当需求强度；
- 不把满意度当付费意愿。

这些不是建议，是 `check` 的输入约束。

## 7. 三种表面的分工

| 表面 | 负责 | 不负责 |
| --- | --- | --- |
| Skill | 模式选择、判断规则、停止条件 | 不执行确定性计算 |
| CLI | 目录、配额、门禁、信号、报告 | 不做研究判断 |
| MCP | 把 CLI 操作送进任何客户端 | 不增加判断、不改结果 |

三者的行为必须一致：CLI 是唯一真值，MCP 只包装，Skill 只解释。
