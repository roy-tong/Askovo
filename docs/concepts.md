# 核心概念

askovo 不以“洞察”或数据量为终点。它先管理**场景 → 用户 → 痛点 → 需求 → 特性 → 产品 → 商业**的推理，再管理**判断与证据之间的距离**。

## 产品与商业推理主链

| 节点 | 核心判断 | 必须额外记录 |
|---|---|---|
| 场景 | 什么触发、环境和任务上下文值得研究 | 场景边界与适用条件 |
| 用户 | 为什么是该场景中的角色、状态和决策角色 | 纳排标准、非用户与反例 |
| 痛点 | 当前替代在哪里失效，造成什么后果 | 替代行为、摩擦成本、无痛点对照 |
| 需求 | 用户要取得什么可观察结果，保持解法中立 | 衡量方式、约束、机会取舍 |
| 特性 | 哪个候选能力能改变结果 | 作用机制、备选方案、接受条件 |
| 产品 | 哪些能力组成有边界的价值交付 | 形态、范围、非目标、验收 |
| 商业 | 这个产品如何形成可验证的商业闭环 | 市场边界、细分、付费者、价格、成本、单位经济、指标和业务门 |

完整定义见[产品与商业推理主链](product-reasoning.md)。节点有证据不等于推导成立，`decided` 也不等于发布就绪、商业成功或因果效果。

## 1. 六类结论

| 类型 | 回答 | 合格证据 | 常见误读 |
|---|---|---|---|
| `need` | 谁、在什么场景、有什么未满足任务与替代成本 | 现场观察、访谈、日记、替代行为、工单 | 功能请求=需求；个案=普遍 |
| `acceptance` | 用户是否理解、接受或拒绝方案 | 概念测试、原型反馈、概念—产品匹配 | 喜欢=会用/会买 |
| `usability` | 能否完成任务、是否易学低错 | 任务成功/耗时/错误/恢复、学习曲线、SUS/UMUX-Lite/SEQ | 满意度=任务成功；好用=需求 |
| `performance` | 明确条件下是否可复现达标 | 台架、仪器、实验室、可靠性/环境/版本回归 | 跑分=体验；实验室=场景 |
| `commercial` | 购买、付费、留存、复购、退换、维修 | 订单、预购、队列、复购、RMA、续费 | 口头意愿=交易；相关=因果 |
| `safety` | 使用风险与合规缺口 | 风险分析、专业试验、认证/法规流程、近失事件 | 用户评分=安全；用户试验=认证 |

同一条材料可进入多条证据链，但只能互补，不能互替。

## 2. 证据形式

| 形式 | 例子 | 能支持 | 不能支持 |
|---|---|---|---|
| `self_report` | 访谈、问卷、日记 | 场景、任务、偏好、意愿 | 行为频率、真实交易 |
| `observation` | 现场观察、任务测试 | 真实做法、错误、workaround | 总体比例、动机 |
| `product_interaction` | 原型、Beta、HUT | 使用与学习过程 | 认证、市场规模 |
| `experiment` | A/B、CLT、模拟器 | 特定条件下的差异/因果 | 未测人群、长期效果 |
| `instrument_log` | 遥测、日志、传感器 | 实际采用、异常、暴露 | 动机、因果（无设计时） |
| `lab_report` | 台架、可靠性、环境 | 工程性能、失效 | 用户体验、需求 |
| `transaction` | 订单、复购、RMA | 真实市场后果 | 原因、未购买者 |
| `support_record` | 工单、维修、客诉 | 失效模式、服务成本 | 故障率（无分母时） |

## 3. E0–E5 仍然描述需求/商业证据强度

| 等级 | 材料中直接出现 | 允许的判断 |
|---|---|---|
| E0 | 活动、角色或场景背景 | 场景出现 |
| E1 | 未满足任务、目标或困难 | 问题被表达 |
| E2 | 当前做法、绕行、失败或切换成本 | 替代方案及摩擦 |
| E3 | 对研究方案的明确接受/偏好 | 方案在给定条件下被接受 |
| E4+ | 价格锚点、购买/付费表达 | 直接商业意图 |
| E4− | 拒绝、取消、退货、放弃 | 直接负面商业行为 |
| E5 | 付费持有、部署、持续使用、复购 | 已实现的行为证据 |

可用性、工程性能、安全**不硬塞进 E0–E5**，各自走验收条件；E0–E5 只用于需求与商业链。

## 4. 判断的三种结果

`askovo audit` 与底层 `askovo check` 会逐条给：

| verdict | 含义 | 下一步 |
|---|---|---|
| `supported` | 声称 `validated`，三条链 + 反证齐全 | 可引用，但仍读边界 |
| `exceeds_evidence` | 声称 `validated`，缺链/反证/引用不存在 | 降级或补证 |
| `open` | `hypothesis`/`needs-validation`，尚未声称结论 | 按 `next_test` 补证 |

## 5. “通过”意味着什么

`pass` 只说明：

- 结构与配置门槛过了；
- 证据链在该门槛下自洽；
- 引用可追溯。

不证明：

- 需求真实存在；
- 样本代表总体；
- 市场规模/份额；
- 因果关系；
- 安全/合规。

## 6. 平台数据不等于样本

平台雷达回答“哪里可能有数据、怎么拿、拿得到什么”，不回答“能否代表总体”。

- 平台可用性分 `supported` / `limited` / `blocked`；
- 评论/帖子/工单是自选择样本；
- 跨平台去重后仍不是概率样本；
- 遥测有暴露分母但缺动机；
- 实验室/认证与用户证据分层。

## 7. 禁止推断

默认写进 `study.json`：

- 不从便利样本推断总体流行度；
- 不把记录当独立用户；
- 不把检索地区当常住地；
- 不把功能提及频率当需求强度；
- 不把满意度当付费意愿；
- 不把可用性/性能/安全证据升级为需求证据。

## 8. 三种表面

| 表面 | 负责 | 不负责 |
|---|---|---|
| Skill | 模式选择、判断规则、停止条件 | 不执行确定性计算 |
| CLI | 路由、目录、配额、采集、分析、门禁、交付 | 不做研究判断 |
| MCP | 把同一组命令送进任何客户端 | 不增加判断、不绕过安全门 |

三者的行为必须一致：CLI 是唯一真值，MCP 只包装，Skill 只解释。
