# 产品创新岗位操作系统：80 岗位族 × 10 生命周期 × 10 行业

更新日期：2026-11-04。

这套能力解决的不是“再列一份岗位名称”，而是 Askovo 当前缺少的执行业务逻辑：**谁牵头、谁协作、输入什么、按什么 SOP 做、产出什么、如何衡量、由谁验收、交给谁、什么结论不能由此推出。**

## 1. 产品架构：一条主链，四层岗位能力

Askovo 的唯一产品与商业推理主链不变：

> 场景 → 用户 → 痛点 → 需求 → 特性 → 产品 → 商业

`04-findings/product-reasoning.json` 仍是唯一机器真值；`demand-judgments.json` 仍管理需求与商业证据资格。岗位系统围绕主链增加四层：

| 层 | 回答 | 产品实现 |
|---|---|---|
| 业务流程 What | 当前处于哪个创新阶段，要改变什么决定 | 10 个生命周期板块、入口/出口条件、可回流工作流 |
| 岗位合同 Who | 谁负责、谁协作、谁复核、交接什么 | 80 个岗位族、职责、RACI、上下游交接、人类边界 |
| 专业实践 How | 具体怎样执行，怎样算做好 | 每岗 SOP、KPI 公式与护栏、质量门、核心产出和模板 |
| 行业上下文 Context | 同一工作在不同产品领域如何变化 | 10 个行业覆盖层：对象、输入、原型、验证、放行人 |

**岗位完成度不是产品结论完成度。** SOP 全部勾选也不能自动把需求标为 `validated`，不能代替 E1/E2 + E3 + E4+/E5 证据门，更不能代替工程、安全、临床、法规、量产或商业放行。

## 2. 十个生命周期板块不是十个孤立部门

| ID | 岗位 | 核心问题 | 主要交接 |
|---|---|---|---|
| L01 市场、产业与机会研究 | R01–R08 | 哪个市场/需求/技术机会值得投入 | 机会边界、规模口径、替代、技术/法规/商业约束 → L02/L03 |
| L02 用户、消费者与需求研究 | R09–R24 | 谁在什么场景有什么问题，证据是什么 | 场景、角色、任务、替代、痛点、需求、反证 → L03/L04 |
| L03 产品战略、管理与需求规划 | R25–R35 | 做什么、不做什么、为何、如何取舍 | 路线图、业务案例、需求基线、优先级、验收 → L04–L07 |
| L04 概念、创新与服务设计 | R36–R43 | 有哪些可比较、可验证的解决方案 | 概念组合、服务蓝图、价值主张、测试假设 → L05/L08 |
| L05 数字产品与体验设计 | R44–R55 | 用户怎样理解、操作、恢复并完成任务 | IA、流程、界面、内容、设计系统、AI 交互、原型 → L08/L09 |
| L06 实体产品与工程定义 | R56–R65 | 物理和技术能力怎样实现并受约束 | ID/CMF、系统需求、结构/电子/固件、DFM、包装规格 → L08/L09 |
| L07 消费品研发与商品设计 | R66–R71 | 配方、感官、材料、版型与包装怎样形成商品 | 配方/食品/感官/香氛/服装/包装方案及样品 → L08/L09 |
| L08 测试与效果验证 | R72–R76 | 是否有价值、可用、可靠、安全并可规模交付 | 分层验证报告、缺口、残余风险、复测条件 → L03/L09 |
| L09 交付与生命周期经营 | R77–R78 | 怎样落地、上市、迭代、组合经营和退出 | 发布/NPI、配置变更、SKU/组合、EOL → 主链与运营回流 |
| L10 研究与设计基础设施 | R79–R80 | 知识、样本、资产、流程和标准怎样复用追溯 | 研究/资产知识库、招募与治理、质量运营 → 全生命周期 |

L10 是横向基础能力，不是“最后一步”。任何反证、配置变更或新场景都可以重开上游岗位；流程不是只允许向前的瀑布。

## 3. 每个岗位族的完整数据合同

每个岗位都在 `skills/askovo/assets/role-catalog.json` 中定义：

1. **身份与别名**：`R01–R80`、中文名、英文名、行业常用岗位名，避免只靠招聘标题匹配；
2. **使命与职责**：岗位对什么业务决定负责，明确不拥有什么结论；
3. **KPI**：名称、公式/观察口径、反作弊与解释护栏，不内置万能目标值；
4. **SOP**：每一步的输入、动作、输出和质量门；
5. **核心交付物**：稳定 ID、用途、模板章节、验收检查；
6. **主链映射**：该岗位支持哪些 scene/user/pain/need/feature/product/business 节点；
7. **交接**：上游与下游岗位，项目执行时再补具体版本、Owner、验收与重开条件；
8. **人工边界**：哪些判断需要实验、设施、专业软件、有资质人员或正式批准；
9. **行业覆盖**：对关键岗位补充行业化实践和额外质量门。

这不是官方职业目录，也不要求企业设置 80 个 headcount。一个人可兼任多个角色，但“自己提出、自己验证、自己批准”的高风险冲突不能被兼任隐藏。

## 4. 十个行业覆盖层：同名工作不等于同一专业

| 行业 ID | 代表性岗位组合 | 核心设计输入 | 验证重点 |
|---|---|---|---|
| `consumer_software` 消费软件 | C 端 PM、UXR、交互、增长 | 用户故事、任务流、功能验收、埋点 | 价值、可用性、功能、留存、付费 |
| `enterprise_software` 企业软件 | B2B PM、BA、服务设计、解决方案 | 组织流程、角色权限、业务规则、接口、ROI | 业务价值、角色任务、集成、安全、迁移 |
| `ai_native` AI 原生 | AI/Agent PM、模型评测、AI 交互、安全 | 任务边界、能力声明、工具权限、评测集、恢复与成本 | 正确性、任务可靠性、权限、人机协同、线上质量 |
| `smart_hardware` 智能硬件 | 硬件 PM、ID、系统、嵌入式、人因 | 整机规格、BOM、功耗、软硬件接口、配置基线 | 体验、性能、可靠性、安全、量产 |
| `traditional_hardware` 传统硬件 | 产品企划、ID/CMF、结构、材料、包装 | 外观、材料、尺寸、人因、制造与包装要求 | 耐用、人因、材料安全、运输、成本 |
| `cpg` 快消品 | 消费者洞察、NPD、配方、感官、包装 | 配方、功效、感官、剂量、包装、价格带 | 偏好、功效、稳定、安全法规、复购 |
| `apparel_home` 服装家居 | 趋势、服装/面料/版型、商品企划 | 款式、面料、版型、尺码、工艺、SKU | 试穿、舒适、材料工艺、产前一致性、组合经营 |
| `industrial_robotics` 工业设备 | 行业研究、BA、系统 PM、系统工程、安全 | 工序、任务包线、节拍、接口、安全、TCO | 任务成功率、现场节拍、可靠性、集成、ROI |
| `automotive` 汽车交通 | 整车规划、座舱 PM、HMI、系统工程 | ODD、误用、整车需求、HMI、配置与安全目标 | 诊所/模拟器/场地/道路分层、安全法规、生产 |
| `medical_health` 医疗健康 | 医疗 PM、临床需求、人因、质量法规 | 预期用途、用户/使用/环境、使用风险、临床证据 | 临床价值、使用安全、性能、监管与质量体系 |

例如：

- 软件 Product Designer 主要支持数字体验、交互和界面；
- 硬件 Product Designer 往往对应 R56 工业设计，而不是 R44 用户体验设计；
- 食品与日化的产品设计可能需要 R66/R67 配方与食品研发、R68 感官、R69 香氛/风味；
- 服务产品不能只画 App，需要 R39 将客户行动、前台、后台、支持流程和物证放在同一蓝图中。

## 5. 可执行产品功能

### 5.1 岗位检索与岗位卡

```bash
askovo roles list --json
askovo roles list --lifecycle L02 --query "访谈"
askovo roles show R29 --industry ai_native
askovo roles show "UX Researcher" --industry medical_health
```

岗位卡包含职责、KPI、完整 SOP、交付模板章节目录、上下游和专业边界。行业化后会同时展示该行业的对象、设计输入、原型、验证层和放行人。

### 5.2 按目标、任务与产品组队，而不是每次都上全套岗位

```bash
askovo roles recommend "开发 AI 摄影应用，验证智能构图与失败恢复" --stage concept
askovo roles recommend "仓储搬运机器人现场工序与 ROI" --stage concept --task decide --scale lean
askovo roles recommend "洗衣液配方与包装样品" --stage prototype --task design
askovo roles recommend "智能相机 DVT 可靠性与安全验证" --stage validation --task validate
```

系统先从目标、阶段和显式 `--task` 判断本次工作类型：

| 任务 | 典型输出 | 默认协作 |
|---|---|---|
| `decide` 决策与取舍 | 1–3 页决策备忘 / Business Case | 1–3 岗 |
| `discover` 发现 | 研究简报 / 机会地图 | 1–3 岗 |
| `define` 定义 | 需求规格 / PRD | 3–5 岗 |
| `design` 设计 | 方案说明 + 设计/工程规格 | 3–5 岗；高风险实体设计最多 6 岗 |
| `validate` 验证 | 分层验证报告 + 放行/缺口 | 3–5 岗；DVT/安全/临床最多 6 岗 |
| `launch` 上市 | 发布/NPI 方案 + 回滚 | 3–6 岗 |
| `operate` 运营 | 生命周期看板 + 行动清单 | 1–3 岗 |
| `review` 审查 | 审计备忘 + 补证/整改 | 1–3 岗 |

选岗顺序固定为：**牵头岗位 → 任务关键词触发的专业岗位 → AI 等能力覆盖岗位 → 当前任务阶段真正需要的行业岗位**。`--scale lean|standard|cross_functional` 可覆盖自动规模。系统同时输出：

- 选中的最小充分团队与逐岗理由；
- 本轮暂不纳入的岗位及原因；
- 真实交接边、行业质量门与主链真值路径。

推荐是分工草案，不会编造团队、目标或产品结论。问题明确触发的专业岗位和牵头岗位不会被人数上限静默截掉；被裁剪的是“本轮不需要的行业角色”，不是质量门。

### 5.3 输出内容与表达方式也由任务决定

推荐结果和工作包都带有 `output_plan`：

- 主交付物及其负责岗位；
- 必要支撑产出（最多两个）；
- 文档格式、建议篇幅、主要读者、语气与语言；
- 必填章节结构；
- 证据呈现方式、适用的图表；
- 表达禁忌；
- 行业优先产出形态（如 AI 的评测/权限/接管、硬件的规格/验证、快消的配方/感官/HUT）；
- 每个已选岗位本轮的主责产出。

例如：软件“是否做付费试点”输出决策备忘而非完整 PRD；AI Agent 概念输出能力边界、评测与失败恢复；硬件 DVT 输出分层验证报告与放行/缺口；快消配方输出配方/感官/包装与合规清单。

### 5.4 生成按任务裁剪的项目执行包

```bash
# 单链：根据 study 的决策问题、产品、阶段自动判断任务并组队
askovo roles scaffold ./study

# 显式指定任务与规模
askovo roles scaffold ./study --task define --scale standard

# 显式指定角色；第一个为 Accountable 牵头角色
askovo roles scaffold ./study --role R29 --role R52 --role R72

# 多链：必须明确工作线程
askovo roles scaffold ./study --chain PR02 --role R29 --role R52
```

空链拒绝生成；单链自动绑定，多链必须传 `--chain`。系统先在临时目录完整构建，再一次性重命名提交到 `01-sources/role-workbench/`：

```text
workplan.json       任务、规模、输出合同、目录/行业哈希、角色/SOP/KPI/模板引用、PRxx.node/edge
workplan.md         输出合同、RACI、KPI 合同、逐步 SOP、真实交接与模板链接
templates/Rxx-Dyy.md 只生成本轮主交付与必要支撑模板
```

默认只生成主交付 + 最多两个支撑模板；需要全部岗位模板时显式加 `--all-templates`。KPI baseline/target/窗口/分母/数据源/Owner 初始为 null，SOP 初始为 `not_started`。主链、需求判断和证据在生成前后逐一比较。已有 stateful workbench 默认拒绝覆盖，传 `--force` 也不能抹掉人工状态；写盘失败不留下半套执行包。

### 5.5 单独生成方案模板

```bash
askovo roles template R52 --deliverable R52-D01 --output agent-interaction-spec.md
askovo roles template R39 --industry enterprise_software
```

模板包括文档负责人、复核人、关联 chain/node/context、岗位特定章节、证据引用格式、质量检查、交接与专业边界。七节点语义字段标记 `editable=false`，正式内容只能来自主链投影；工程/实验等专业执行记录可以填写，但不能新写市场、需求、产品或商业结论。未知保持空值，不自动填 0 或“已验证”。

### 5.6 从唯一主链生成交付投影

```bash
askovo deliver ./study --kind role --role R52
askovo deliver ./study --kind role --role R09 --deliverable R09-D01 --industry medical_health
askovo deliver ./study --kind role --role R52 --chain PR02
```

正式岗位交付先运行新的 full audit，再只读投影 workplan 绑定的 chain/node；没有 workplan 的旧研究仅支持单链或显式 `--chain`。statement、rationale、status、assumptions 和 evidence IDs 都来自主链，输出为扁平的 `06-report/role-Rxx-Dyy.md`，进入现有新鲜度与边界检查。文件开头先呈现 workplan 的输出合同（格式、篇幅、读者、章节、证据呈现与表达禁忌），再投影主链；不会因为格式简化而改变证据边界。目录/行业哈希过期、绑定损坏或 KPI 目标缺口径会阻断；没有 `--role` 或主链也会阻断。模板章节标记 `editable=false` 并给出来源映射，工作备注独立分区。

### 5.7 生命周期导航与新鲜度

```bash
askovo deliver ./study --kind lifecycle
```

`06-report/lifecycle-board.md` 展示 10 个板块的入口/出口、牵头/协作、主责产出、实际 Owner、SOP 作业状态和真实交接边，不计算一个掩盖失败的“整体完成率”。workplan 变化会影响相关报告新鲜度；岗位目录和行业资产变化只让 role/lifecycle 投影过期，不拖脏其他报告。`chat_summary.reproduce_command` 保留角色、模板、行业和链参数。

## 6. KPI 不是文档产量，也不是自动评分

岗位目录提供 KPI 的**定义**，不提供跨行业通用 benchmark。团队必须另填 baseline、target、时间窗、分母、数据源和 Owner。收入、复购、ROI、转化等商业 KPI 设定目标时还必须引用主链 `business.success_metrics` 的 `business_metric_ref`，岗位层不另算一套商业事实。

| 错误激励 | Askovo 的替代口径 | 必要护栏 |
|---|---|---|
| 写了多少访谈/报告 | 决策关键判断可追溯覆盖、反证处理、补证后决策变化 | 引用多不代表证据强；不得删除负例 |
| 完成了多少需求 | 需求验收与追溯覆盖、变更影响闭环 | 验收通过不证明需求值得做 |
| 设计交付多少页面 | 核心任务完成、错误恢复、可访问性与工程复用 | 视觉一致不等于任务价值 |
| Agent 调用了多少工具 | 版本化任务集上的正确完成、接管与失败恢复、成本 | 工具调用完成不等于业务结果正确 |
| 工程通过多少测试 | 绑定配置的需求验证覆盖、失效关闭与回归 | 工程通过不证明用户价值或发布就绪 |
| 招募速度/样本量 | 合格参与者到研究率、角色覆盖、数据质量与隐私 | 不能以速度牺牲抽样和知情同意 |
| 研究复用次数 | 有决策上下文和有效边界的复用、避免重复研究 | 旧证据不能脱离时间/场景/版本硬套 |

KPI 目标在生成执行包时为 `null`，不是 0；任何自动计算都需要明确分母和时间窗。便利样本比例不能变成绩效中的“市场普及率”。

## 7. 五类验证必须分开

1. **价值验证**：是否需要、是否接受、是否发生真实购买/部署/保留；
2. **体验验证**：是否理解、能否完成任务、错误后能否恢复；
3. **功能与工程验证**：特定配置是否满足性能、接口、可靠性与环境规格；
4. **安全/临床/法规验证**：适用证据、风险控制、质量体系和授权人员是否满足要求；
5. **生产与交付验证**：能否稳定、经济、可追溯地重复交付。

因此：

- E3 概念接受不能成为发布许可；
- EVT/DVT/PVT 不能替代需求证据；
- 感官喜好不能替代功效、安全和保质期；
- 实验室任务成功不能替代工业现场节拍和 ROI；
- 医疗产品可用性不能替代临床有效性或监管批准；
- `decided` 只是选择记录，交付、观察结果、因果状态仍独立。

## 8. 四个端到端工作流示例

### 8.1 AI 摄影应用

R01/R04 机会与替代 → R09/R14 拍摄选片修图行为 → R29 定义任务/模型/工具边界 → R38 比较概念 → R44/R46/R52 拍摄流程、解释确认和失败恢复 → R55 体验原型 → R72/R73/R75 概念、可用性、版本化任务与性能评测 → R27/R34/R77 迭代、商业化与发布。

关键门：图像质量与任务正确性由领域评测确认；演示成功不能替代评测；AI 推荐可解释不等于推荐正确；付费转化与留存分开观察。

### 8.2 AI 智能相机

R01/R06 市场与技术路线 → R09/R13/R22 场景、姿势、握持、携带与续航 → R30/R61 整机规格与系统需求 → R56/R57/R58/R59/R60 外观、CMF、结构、电子、固件 → R52/R62 端侧 AI 与实体/App 交互 → R64/R65 DFM 与包装 → R73/R75/R76 试用、工程和安全质量 → R77 NPI。

关键门：所有结论绑定 HW/FW/BOM/工艺配置；手板偏好、实验室性能、现场好用与量产一致分别签收。

### 8.3 新型洗衣液

R03/R10/R20 品类、消费者和价格 → R13/R23 家庭洗涤与感官 → R31 定义功效、规格、定位与目标成本 → R66/R68/R69 配方、感官与香型 → R65/R71 包装结构、剂量和视觉 → R72/R74/R76 概念、HUT、稳定/质量/法规 → R77/R78 量产上市与商品组合。

关键门：免费样品使用不是复购；香味偏好不是清洁功效；实验室稳定不等于全货架期；宣称由法规与质量人员复核。

### 8.4 仓储搬运机器人

R02/R08 行业工序与商业案例 → R19/R35 组织决策链、业务流程与需求 → R30/R61 任务包线、载重、速度、接口与系统规格 → R58/R59/R60/R63 机电与控制方案 → R52/R62 操作、异常、急停与接管 → R75/R76 现场性能、可靠性与安全 → R08/R77/R78 TCO、试点交付与生命周期。

关键门：采购、现场、操作员、EHS、IT/OT 和维护者分别表达并验收；实验工位成功不代表现场节拍；部署不等于财务确认的 ROI。

## 9. 方法来源与设计边界

岗位地图是 Askovo 的综合工作分类，不是官方职业标准。方法锚点包括：

- [2020 Scrum Guide](https://scrumguides.org/scrum-guide.html)：Product Owner 对产品价值、Product Goal、Backlog 排序与透明度的责任；
- [Stage-Gate 官方模型](https://www.stage-gate.com/blog/the-stage-gate-model-an-overview/)：跨职能并行工作、Go/Kill/Hold/Recycle 与下一阶段资源承诺；
- [NN/g Contextual Inquiry](https://www.nngroup.com/articles/contextual-inquiry/)：自然情境观察、共同解释与真实工作实践；
- [NN/g Service Blueprints](https://www.nngroup.com/articles/service-blueprints-definition/)：客户行动、前台、后台、流程与物证的关系；
- [FDA 2026 年 8 月人因指南](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/applying-human-factors-and-usability-engineering-medical-devices)：预期用户、用途、环境、界面与使用相关风险共同进入设计和验证；
- 既有[五域方法论](product-methodology.md)中的 ISO/IEC/IEEE 29148、ISO 11136、AAPOR、ESOMAR、IIBA 等来源。

这些资料支持职责、流程和方法设计，**不提供通用 KPI 目标，也不证明 Askovo 自动具备任何专业签字资格**。
