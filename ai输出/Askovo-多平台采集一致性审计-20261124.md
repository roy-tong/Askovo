# Askovo 多平台采集一致性审计

日期：2026-11-24

## 结论

**Askovo 也存在类似问题，而且不只是“合规口径过严影响业务”。更严重的是：路线治理存在双重标准、失败可被误判为成功、平台与证据字段不统一、独立采集器绕过统一合同。**

本次共确认 **22 项问题**：9 项高优先级执行/数据正确性问题、11 项平台与契约问题、2 项文档与测试问题。审计只读，未修改代码、目录或测试，未进行真实平台采集。

## 范围与方法

- 主引擎：`sure_engine.py` 的 API、CDP、manifest、CLI、queue 路径。
- 独立采集器：GitHub、Reddit/Arctic/PullPush、YouTube、Hacker News、Amazon、Kickstarter、Discord，以及公共 helper、轮转和下载工具。
- 注册表：`platform-catalog.json`、`platform-field-notes.json`、`open-source-connectors.json`。
- 文档与测试：连接器合同、采集手册、实现状态、相关 unittest。
- 本地模拟验证：无 scope/adapter 的 CDP 写入、通用 CDP 零输出、YouTube 搜索失败、CLI 失败状态退出码；没有网络请求。
- 全量基线：`Ran 914 tests`，913 通过、1 失败；相关平台测试 47 项全部通过。

## 一、高优先级执行与数据正确性问题

### P0-01：`collect_cdp` 直接调用可绕过 scope/adapter 检查

- **证据**：`skills/askovo/scripts/sure_engine.py:8558` 只检查 `ack_terms`、目录 `cdp` 和 URL；`collect_platform:8913-8936` 才检查 `scope.allowed_sources` 与 adapter enabled。
- **模拟结果**：`allowed_sources=[]`、`source_adapters={}` 时，直接调用 `collect_cdp` 仍返回 `collected / records=1`。
- **影响**：CLI 正常入口之外的调用方可绕过 Design gate 和授权边界。
- **建议**：将 scope/adapter 校验下沉到 `collect_cdp`，而不是仅放在包装函数；增加无 scope、无 adapter、disabled 三组拒绝测试。

### P0-02：多个 CDP 失败状态在 CLI 中返回 0

- **证据**：`cli_collect:10031-10056` 的非零映射遗漏 `cdp_timeout`、`blank_render`、`page_not_found`、`scope_violation`、`session_drop`、`session_expired`、`cooldown`。
- **模拟结果**：这些状态均实际返回 exit 0。
- **影响**：外部调度可能把超时、空渲染、越权和掉线当成成功。
- **建议**：建立统一终态到退出码的映射，所有非 `collected` 除明确的 `planned/dry-run` 外默认非零，避免新增状态再次漏配。

### P0-03：通用 CDP 零输出被写成 `collected / completed`

- **证据**：`collect_cdp:8669-8687` 在零行且页面有标题时继续，最终 `:8756-8787` 写 run；manifest 默认 `stop_reason=completed`。
- **模拟结果**：选择器无输出时返回 `collected / records=0 / stop_reason=completed`。
- **影响**：选择器失效、登录墙未被识别或页面无数据都可能被当成空语料完成，污染采集漏斗。
- **建议**：采用 Discord 的 `empty_unconfirmed` 口径；零输出必须有独立状态，只有确认空页面/空频道才允许 completed。

### P0-04：YouTube 请求失败仍推进查询断点

- **证据**：`collect_youtube_innertube.py:47-70` 对 403/429 和其他异常返回 `None`；`:280-319` 将空搜索当成零视频，最后仍追加 `queries_run`。
- **模拟结果**：搜索失败后输出 `DONE total_new=0`，同时 `queries_run=['synthetic failure']`。
- **影响**：下一次运行会跳过失败查询，形成永久性假完成。
- **建议**：区分 empty、partial、failed；失败查询不得进入 `queries_run`，必须记录错误并可重试。

### P0-05：HN、Arctic、PullPush 请求失败被当成部分成功

- **证据**：`collect_hn.py:86-90`、`collect_arctic_reddit.py:102-106`、`collect_pullpush_reddit.py:86-90` 捕获异常后仅打印 warning 并 break，主函数仍写出并正常结束。
- **影响**：调用方无法区分真实空结果、部分覆盖与传输失败，可能错误放大样本代表性。
- **建议**：返回结构化 `status/partial/errors/stop_reason`，失败时非零退出；manifest 必须显式记录未完成窗口。

### P0-06：legacy 的 `primary_sample_eligible` 与文档不一致

- **证据**：`collect_legacy_reddit.py:22-24,171-173` 和工具箱 README:359-362 要求 legacy 一律 `primary_sample_eligible=false`；但 `collect_arctic_reddit.py:75`、`collect_arctic_windows.py:164`、`collect_pullpush_reddit.py:63` 按日期放行，未配置窗口时通常为 true。
- **影响**：非官方历史数据可能进入主样本，与官方 API 数据混层，直接影响证据等级。
- **建议**：统一 legacy 为 false，后续只能经具名上下文审核提升；增加跨采集器合同测试。

### P0-07：独立采集器不满足统一 raw/manifest 合同

- **证据**：`connector-contract.md:5-20,52-88` 要求每 run 三份产物、revision 和 source envelope；多个采集器使用 `record_id` 而非 `source_record_id`、`text_hash` 而非 `normalized_text_hash`，且缺 `collection_run_id`、`connector_revision` 和 manifest。HN 甚至没有 run ID/source_tier。
- **影响**：独立工具的输出不能直接按统一证据链消费，字段映射和审计依据依赖人工理解。
- **建议**：所有采集器共用同一 manifest writer 与 raw envelope schema；禁止各自发明字段名，兼容输出必须通过显式适配层。

### P0-08：YouTube 路线存在第一方/第三方双重标准

- **证据**：`open-source-connectors.json:227-263` 将第三方非官方评论/字幕抓取器 blocked；`collect_youtube_innertube.py:43-69` 使用同类非官方 innertube 端点；`platform-field-notes.json:1685` 明确写着“project-internal and not covered by the API terms; treat its volume as unlicensed headroom and keep it small”。
- **影响**：同一访问机制因代码归属不同而得到不同结论，准入审查失去一致性；该路线目前缺少与其他连接器等价的授权依据。
- **建议**：单独做 YouTube 路线决策：优先官方 API；若保留 innertube，必须明确受限层级、访问依据、规模、数据权利和 blocked/limited 状态，不能用“第一方脚本”豁免审查。

### P0-09：空正文 Issue 被误判为 `self_report_text`

- **证据**：`sure_engine._raw_text:2074-2085` 会让 title-only 记录获得文本；`issue_structuring.py:687-702` 据此设置 `self_report_text`，与 A15“no quotable body text means unverified”及测试预期冲突。
- **全量失败**：`test_no_reproducible_text_stays_unverified` 实际返回 `self_report_text`，期望 `unverified`。
- **影响**：标题本身可能被当成可引用证据，抬高材料的可信基础。
- **建议**：明确 title 与 body 的证据语义；空 body 不得因 title fallback 变成 self-report，修复实现或正式修订合同，不能仅改测试。

## 二、平台与契约问题

### P1-01：Hacker News 平台 ID 不一致

- **证据**：目录使用 `hackernews`，`collect_hn.py:40` 写 `source_platform=hacker_news`。
- **影响**：按平台聚合、字段校验和来源映射可能分裂为两个平台。
- **建议**：统一为 `hackernews`，旧数据通过显式别名迁移，不新增隐式映射。

### P1-02：Amazon 数据集 ID 与平台 ID 不一致

- **证据**：目录使用 `amazon`，`collect_amazon_reviews_2023.py:116` 写 `amazon_reviews_2023`。
- **影响**：历史数据可能和实时 Amazon 数据分成不同平台，但文档没有定义这种命名映射。
- **建议**：`source_platform=amazon`，用 `source_family=amazon_reviews_2023_historical` 表达数据集。

### P1-03：Amazon、Bilibili 的 CDP 目录自相矛盾

- **证据**：Amazon `platform-catalog.json:279-300`、Bilibili `:464-483` 均为 `cdp: true`，但 `access_modes` 没有 `cdp_visible_page`。
- **模拟枚举**：缺失项正是 `['amazon', 'bilibili']`。
- **影响**：目录、策略卡、Design 校验和调用方对 CDP 能力的理解不一致。
- **建议**：补齐 access mode，并增加 `cdp:true ⇒ access_modes 包含 cdp_visible_page` 的注册表不变量测试。

### P1-04：`supported` 与主 CLI 的实际采集能力不一致

- **证据**：YouTube、Hacker News 目录为 supported，但 `adapter=none`；主 `collect` 实际返回 `adapter_unavailable`。独立工具箱又存在对应采集器。
- **模拟结果**：两个平台均实际返回 `adapter_unavailable`。
- **影响**：业务侧看到 supported 以为可直接运行，实际必须改走 fixture、CDP 或独立脚本。
- **建议**：把“准入决策”“主 CLI 内置适配器”“独立工具”“CDP 路线”拆成不同字段，文档逐项说明；不要用 adapter=none 掩盖实现差异。

### P1-05：主 `collect` 直连 API 没有使用队列限速

- **证据**：`_collect_github:7596-7627`、`_collect_reddit:7652-7684` 无请求间隔或 Retry-After 处理；`DEFAULT_RATE_SECONDS` 只在 queue 的 `run_queue` 使用。
- **影响**：直接调用 collect 比 queue 更容易突发请求并触发限流，同一平台两条入口的行为不同。
- **建议**：把限速和 403/429 分类退避下沉到连接器本身，queue 只做编排。

### P1-06：公共 `request_json` 的退避与错误信息不符合统一规则

- **证据**：`common.py:64-79` 对 403/429 只按固定 1.5s 倍数重试，不读 Retry-After；最终错误包含完整 URL。
- **影响**：可能放大限流；若 URL 带 token/query 秘密，错误日志有泄露风险。
- **建议**：复用 `classify_backoff`，URL 查询参数默认脱敏，保留状态码与分类原因。

### P1-07：manifest 的开始时间不是实际开始时间

- **证据**：CDP manifest 在采集完成后才设置 `started_at` 和 `finished_at`（`sure_engine.py:8758-8771`），普通 API 也在采集完成后设置（`:8975` 附近）。
- **影响**：无法从 manifest 计算真实执行时长、超时点和恢复窗口。
- **建议**：进入采集前记录 started_at，结束时记录 completed_at；raw write 失败增加 write_failed_at。

### P1-08：独立工具跨 run 去重与续跑合同不一致

- **证据**：`collect_arctic_reddit.py:167`、`collect_hn.py:131`、`collect_pullpush_reddit.py:140` 都是 `append=False`，去重仅在当前进程内；工具箱文档却描述跨 run 去重和断点能力。
- **影响**：同路径重跑可能覆盖历史输出，不能兑现跨 run 去重和增量研究。
- **建议**：明确哪些工具支持 append/resume，统一加载已有 record_id/text_hash，失败时不覆盖最后一份有效结果。

### P1-09：YouTube 的全局 cap 和状态写入不可靠

- **证据**：`--max-records` 只在查询循环顶部检查（`collect_youtube_innertube.py:277-279`），评论循环内不检查；state/output 直接写入且父目录未确保存在（`:265-275,315-319`）。
- **影响**：全局上限可能被突破，嵌套目录会失败，崩溃可损坏断点。
- **建议**：在 record 写入处执行 cap，使用 `ensure_parent` + `atomic_write_json`，并测试 cap 边界和崩溃恢复。

### P1-10：Arctic Windows 断点非原子且缺父目录处理

- **证据**：`collect_arctic_windows.py:263-277` 直接 `write_text`，未使用已有 `atomic_write_json`；out/state 的 parent 未自动创建。
- **影响**：中断可损坏 state，首次按文档目录运行可能失败。
- **建议**：统一原子写和父目录创建；恢复时先验证 JSON，损坏状态不得静默当空状态。

### P1-11：Amazon manifest 工具未锁定 revision

- **证据**：`amazon_reviews_2023_manifest.py:33-36` 固定请求 `/tree/main`，无 revision 参数；输出只有文件 oid，没有 dataset revision。
- **影响**：规划下载时无法保证与后续 reviewed commit 完全一致，违背“先审查固定版本再采集”的合同。
- **建议**：要求完整 commit SHA，请求 `/tree/<revision>`，manifest 顶层保存 dataset_revision 并校验后续下载一致。

## 三、文档与测试问题

### P2-01：多份文档已经互相陈旧或矛盾

- `docs/connectors.md:30-38` 的“当前内置采集适配器”只列 GitHub/Reddit，但后文 `:127-138` 已有多类第一方工具；需要明确主 CLI 与独立脚本的区别，而不是只改一句支持数量。
- `docs/connectors.md:45` 把 Kickstarter 写作 blocked，目录 `platform-catalog.json:653` 实际为 limited + CDP。
- `connectors/README.md:365-373` 说 legacy 未登记进 `open-source-connectors.json`，但注册表 `:51-76` 已包含 `reddit-arctic-shift-historical`。
- `docs/connectors.md:62` 仍写“截至 2026-08-27”，而目录与注册表已更新到 2026-11。

### P2-02：现有测试未覆盖关键不变量，且基线有一项证据门失败

- 相关平台 47 项测试全部通过，但没有覆盖：直接 `collect_cdp` 的 scope 绕过、CDP 失败退出码、零输出 completed、YouTube 失败推进断点、legacy primary eligible、cdp/access_modes 一致性、raw schema 一致性。
- 全量基线 914 项中已有 1 项失败（P0-09），所以当前不能把“全量绿”作为交付依据。

## 建议修复顺序

1. **先统一结果语义**：`collected / partial / empty_unconfirmed / failed / challenge / scope_blocked`，零输出不自动 completed，失败必须非零退出。
2. **把授权检查下沉**：`collect_cdp` 自身完成 scope、adapter、Design gate，不能依赖包装函数。
3. **失败不得推进状态**：YouTube 搜索、分页、窗口、manifest 失败均不可进入 completed/queries_run。
4. **统一证据合同**：平台 ID、raw envelope、source_tier、primary_sample_eligible、collection_run_id、connector_revision 和真实时间戳共用一个 writer。
5. **单独裁决 YouTube 路线**：官方 API 优先；innertube 若保留，必须明确 limited 层级与审查依据，并与其他 blocked 第三方路线采用同一标准。
6. **补齐目录和文档**：Amazon/Bilibili access_modes、主 CLI 与独立工具能力矩阵、Kickstarter 状态、Arctic 注册状态。
7. **把上述行为写成合同测试**：尤其 P0-01 至 P0-09，先红后绿，再修复现有空正文证据门失败。

## 与 Growovo 审计结论的区别

Growovo 的主要问题是“合规口径直接阻断业务动作”；Askovo 还存在“同一合规标准在不同实现中执行不一致”。**不建议把 Growovo 的‘合规只提示’机械复制到 Askovo 的采集层。** 采集涉及访问授权、数据权利和证据可信度，正确方向是统一业务结果和审查标准，而不是简单绕过所有边界。


## 七、修复落地记录

本节记录本次对全部 22 项问题的实际修改，不把修复计划当成完成结果。

### 执行与结果语义

- `collect_cdp` 自身执行 scope 和 enabled adapter 检查，直接调用不再绕过授权；`empty_unconfirmed` 不写 run，所有非 `collected/planned` 终态均非零退出。
- YouTube、HN、Arctic、PullPush 请求失败显式失败，不再把异常当成空结果；YouTube 空响应、失败搜索和失败评论页均不推进 `queries_run`。
- legacy 来源统一 `primary_sample_eligible=false`；空正文 Issue 保持 `unverified`，不再因标题回退变成 `self_report_text`。

### 证据与审计合同

- 新增共享 `with_connector_envelope` 和 manifest writer，统一 `source_record_id`、`normalized_text_hash`、`collection_run_id`、`connector_revision`、真实开始/完成时间、数量、错误和停止原因。
- Hacker News 使用 `hackernews`，Amazon 使用 `amazon`，Amazon/Bilibili 补齐 `cdp_visible_page`。
- 独立工具改为追加而非覆盖，断点采用原子写；YouTube 全局 cap、父目录和首次失败现场均补齐。
- Amazon manifest 强制完整 reviewed revision，下载 URL 和记录均携带该 revision。

### 平台路线与文档

- YouTube/Hacker News 已接入主 CLI 采集路径，不再出现目录 supported 但实际 `adapter_unavailable` 的矛盾。
- YouTube innertube 明确为 `public_endpoint_limited`：官方 Data API 优先，项目内部路线单独复核，不再使用“unlicensed headroom”表述，也不以第一方身份豁免审查。
- `docs/connectors.md`、`docs/cli.md`、`docs/feature-status.md`、连接器 README、平台目录、field notes 和 CHANGELOG 已同步主 CLI 与独立工具的能力、Kickstarter 状态、Arctic 注册状态及当前日期。

### 新增回归

`tests/test_collection_consistency.py` 覆盖：直接 CDP 授权绕过、失败退出码、零输出、YouTube 假完成、legacy 分层、CDP access mode、平台 ID、空正文证据门、主 CLI 两条新采集路径、manifest 时间、Retry-After、失败清单、跨 run 追加、raw envelope、全局 cap、原子断点和 reviewed revision。`tests/test_askovo_arctic_windows.py` 同步了失败窗口非零退出的新语义。

最终验收结果：`python3 -m unittest discover -s tests` **Ran 954 tests，OK**；`python3 -m ovo_acceptance case validate` 通过（17 cases、28 incidents，零错误）；`case verify` 通过（17 passed / 0 failed / 0 blocked）。`git diff --check` 通过。未执行真实平台采集或外部写操作。
